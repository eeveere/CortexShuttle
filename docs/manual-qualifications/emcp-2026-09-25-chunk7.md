1. **Model quality (blocking acceptance).** In both attempts 7 and 7g the model
   proposed the same patch, byte-identical postimage `f643cfdb…`: it appended an
   `npm run test:mcp` block. `package.json` has no such script, so the patch
   invents a command, breaks "preserve existing npm commands", and never corrects
   the `test:live` guidance the objective targeted. 7g's plan summary differed
   from 7's and the patch did not. The patch is deterministic at temperature 0.
   Whether a different profile helps is out of scope (thinking is a separate
   experiment).
2. **Verification does not cover the change.** `npm run check` passes with the
   invalid guidance; no test reads `AGENTS.md`. A passing check is not evidence
   of a correct doc edit.
3. **Plan defects (fixed in plan `e`, not in the original plan file).**
   `npm.cmd` refused by the executor; plan environment lacked `ComSpec`, `PATH`,
   `TEMP`, `TMP`; verbatim cwd breaks `cmd.exe`; missing `TEMP` made tsx write
   into the workspace. The original `.shuttle/emcp-agents-live-test-plan.json`
   still cannot run.
4. **Executor behavior worth a follow-up.** A refused (`.cmd`) check left the
   action `unknown` with no receipt (attempt 7); the checklist treats that as a
   stop, and this state directory was not recoverable in place. The verbatim
   `\\?\` cwd is a general hazard for Windows child processes. An unfixed
   verification environment that writes into the workspace is only caught
   because the operator inspects `git status`.
5. **Proposal accuracy.** 4B-model planning summaries were partly wrong both
   times (7: `test:live` "runs the MCP stdio test"; 7g: `npm run test` "is" the
   MCP stdio test). Only the operator's review caught this.
