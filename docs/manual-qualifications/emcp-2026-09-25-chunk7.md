## Findings

1. **Wrong patch (blocking acceptance).** Superseded in part by follow-up items
   1–4: the cause is insufficient edit context plus the model's read strategy;
   model capability is not established. In both attempts 7 and 7g the model
   proposed the same patch, byte-identical postimage `f643cfdb…`: it appended an
   `npm run test:mcp` block. `package.json` has no such script, so the patch
   invents a command, breaks "preserve existing npm commands", and never corrects
   the `test:live` guidance the objective targeted. 7g's plan summary differed
   from 7's and the patch did not. The patch is deterministic at temperature 0.
   Whether a different profile helps is out of scope (thinking is a separate
   experiment).
2. **Verification does not cover the change.** `npm run check` passes with the
   invalid guidance; no test reads `AGENTS.md`. A passing check is not evidence
   of a correct doc edit.
3. **Plan defects (fixed in plan `e`, not in the original plan file).**
   `npm.cmd` refused by the executor; plan environment lacked `ComSpec`, `PATH`,
   `TEMP`, `TMP`; verbatim cwd breaks `cmd.exe`; missing `TEMP` made tsx write
   into the workspace. The original `.shuttle/emcp-agents-live-test-plan.json`
   still cannot run.
4. **Executor behavior worth a follow-up.** A refused (`.cmd`) check left the
   action `unknown` with no receipt (attempt 7); the checklist treats that as a
   stop, and this state directory was not recoverable in place. The verbatim
   `\\?\` cwd is a general hazard for Windows child processes. An unfixed
   verification environment that writes into the workspace is only caught
   because the operator inspects `git status`.
5. **Proposal accuracy.** 4B-model planning summaries were partly wrong both
   times (7: `test:live` "runs the MCP stdio test"; 7g: `npm run test` "is" the
   MCP stdio test). Only the operator's review caught this.

## Follow-up diagnosis (2026-09-25)

Read-only analysis of `chunk-7` and `chunk-7g` (journals opened with
`immutable=1`, never through Shuttle) and of emCP files at `a652789`. It
refines findings 1, 4 and 5. Item 3 led the final evidence review to correct
the outcome headline ("twice").

1. **The model never saw the text the objective targets.** The inaccurate
   guidance is `AGENTS.md` L238–242 ("End-to-End Tests … Run against live
   embedding endpoint … Uses `RUN_LIVE_EMBEDDING_TEST=1 npm run test:live`",
   bytes 8108–8290) and L346–350 ("Unit tests only" / "Integration tests only",
   bytes 11531–11643). 7g's three reads were `read_task_text` L1, L60 and L107
   with `line_count` 100, each cut at the 2048-byte excerpt cap: bytes
   0–2048, 2046–4094 and 4039–6087 (excerpt hashes `97496bb6…`,
   `ebe8c6c9…`, `043545aa…`, identical in 7 and 7g; 7g `observation_hash`
   values `e55366b3…`, `4044eea5…`, `6c006cb6…`). Linear reads cannot reach byte 8108 within the
   6144-byte budget. `find_task_text` was offered on turns 1–3 and never used;
   `test:live` occurs at L24, L242 and L350.
2. **The edit context lacked the facts needed to write correct guidance.**
   The planning request included `package.json`'s `scripts` in its preview. The
   edit session's user JSON lists only permitted files, so `package.json` was
   absent from every edit turn and could not be read. `vitest.config.ts` (live
   test excluded unless `RUN_LIVE_EMBEDDING_TEST=1`) and
   `tests/e2e/mcp-stdio.test.ts` (offline, fake embedding server) were never
   declared inputs. The plan summary is not carried into editing. The only
   test text the model saw was the Essential Commands block (L20–24), which is
   already roughly accurate; `npm run test:mcp` was added there.
3. **"Twice" is one sample.** Edit request/1 is byte-identical in 7 and 7g;
   requests 2–4 are identical after substituting the session-derived tool-call
   IDs (`7716d140…`, `efc9fc4e…`). At temperature 0 an identical postimage is
   expected, and the differing plan summaries cannot reach the edit turns.
   The planning prompts differ only in admission, snapshot and plan-revision
   IDs, so the summaries' difference is not evidence of a second sample.
4. **Model capability is not established either way.** Context was
   insufficient, so the rejection does not show the 4B model cannot do the
   task. There is some independent weakness: attempt 7's plan said `test:live`
   runs the MCP stdio test although its own context showed
   `"test:live": "vitest run tests/integration/live-embedding.test.ts"`.
5. **Attempt 7's `unknown` was a projection label, not an uncertain effect.**
   `task-verify-all` records the check binding before preparing the action;
   the `.cmd` refusal happens in `prepare_verification`, before any action row
   exists. `chunk-7` has the binding (`suite/f54b465b…/183c5838…`), no
   verification action and no `verification_actions` row, so nothing was
   started. `task-verify-status` reports `unknown` for any binding without a
   receipt. The state could not be recovered in place because the plan is part
   of the singleton task intake.
6. **The original plan file remains known-broken.**
   `.shuttle/emcp-agents-live-test-plan.json` (`npm.cmd`, `SystemRoot` only)
   must not be used; plan `e` is the working reference until it is replaced.

**Plan `e`.** No gate weakened: same `run check`, declared inputs and limits;
the added variables carry no credentials or home directories; hashing
`node.exe` is at least as strong as hashing the `npm.cmd` shim. Two minor
points: `--prefix C:\dev\agentic\emCP` hard-codes the workspace rather than
binding it to the admitted root, and `npm-cli.js` and `system32` are unhashed,
which the receipt's "undeclared dependencies" limitation already covers. The
7g check ran after the operator had decided to reject; the re-admission reason
says so.

**Attribution.** The rejection is correctly put down to context and model,
not to a protocol defect. It is not wholly outside the protocol: S033's
model-facing projection (`docs/decisions.md`, Chunk 3 clarification 3) sends
edit turns only permitted files, so `package.json` and the plan summary are
excluded by design. The other causes are the plan's declared inputs, inherited
from r4 (no `vitest.config.ts`, no stdio test), and the model reading linearly
instead of calling `find_task_text`. Find excerpts are charged to the read
budget (S033 durable context section), and three 256-byte matches still leave
room for two targeted reads.

**Planning headroom.** The v1 planning turn is still streamed and out of
S033's scope. In 7g it used 34,279 bytes (52% of the 65,536-byte cap) for 148
output tokens, about 230 bytes per token. At `max_tokens` 512, a planning reply
above roughly 280 tokens would hit r4's failure mode on the planning side.

operator observations. The target byte offsets (8108–8290, 11531–11643) were
not read from emCP. They are consistent with the journal: the seen bytes 0–6087
contain no "End-to-End", "Unit tests only" or "Integration tests only";
`test:live` appears there only at byte 486; the file is 11,643 bytes. Receipt
and offer hashes were not recomputed (no BLAKE3 tool available).
